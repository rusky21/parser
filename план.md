# Инженерный план реализации системы лидогенерации и аудита сайтов (Яндекс.Карты + 2ГИС)

## 1. Исходный план (Базовое видение)

### Фаза 1. Проектирование БД и моделей данных (Backend)
#### 1.1. Схема базы данных (SQLite + SQLAlchemy Async)
* **Таблица `organizations`**:
  * `id` (INTEGER PK)
  * `source` (TEXT: 'yandex' | '2gis')
  * `external_id` (TEXT UNIQUE) — уникальный ID точки на картах для предотвращения дублей
  * `name` (TEXT)
  * `address` (TEXT)
  * `rating` (REAL)
  * `reviews_count` (INTEGER)
  * `phones` (JSON/TEXT) — список номеров из карточки
  * `website` (TEXT)
  * `card_url` (TEXT) — прямая ссылка на карточку
  * `created_at` (DATETIME)
* **Таблица `audit_results`**:
  * `id` (INTEGER PK)
  * `org_id` (INTEGER FK $\rightarrow$ `organizations.id`)
  * `status` (TEXT: 'OK' | 'NO_SITE' | 'ONLY_SOCIAL' | 'SITE_DOWN')
  * `has_ssl` (BOOLEAN)
  * `is_adaptive` (BOOLEAN)
  * `has_analytics` (BOOLEAN) — наличие Яндекс.Метрики / GA
  * `detected_cms` (TEXT, nullable)
  * `last_updated_year` (INTEGER, nullable) — копирайт / sitemap / Last-Modified
  * `extra_phones` (JSON/TEXT) — номера, найденные на самом сайте
  * `extra_emails` (JSON/TEXT) — email-адреса с сайта
  * `pitch_text` (TEXT) — готовый оффер для звонка
  * `audited_at` (DATETIME)

### Фаза 2. Модули скрейпинга геосервисов
#### 2.1. Скрейпер Яндекс.Карт (`yandex_scraper.py`)
* **Инициализация**: Playwright `launch_persistent_context` с директорией `./browser_profile`, флагами скрытия автоматизации и рандомным User-Agent.
* **Поиск**: переход на `yandex.ru/maps` $\rightarrow$ ввод запроса (ниша + город) с задержками между нажатиями (40–120 мс).
* **Обход антифрода**:
  * Проверка на селекторы капчи (`.SmartCaptcha`, `iframe[src*="captcha"]`).
  * При срабатывании: отправка события `CAPTCHA_TRIGGERED` через WebSocket на фронтенд, ожидание ручного ввода пользователем в открытом окне.
* **Скроллинг выдачи**:
  * Скролл контейнера списка результатов (`.scroll__container`) случайными отрезками (300–600 px) с паузами 1.8–3.5 сек.
  * Парсинг карточек на лету во время скролла.
  * Фильтрация через SQLite: если `external_id` уже есть в базе — пропускаем.
  * Остановка ровно при достижении 50 новых организаций.
* **Извлечение данных**: название, адрес, рейтинг, ссылка на сайт, исходные телефоны, ссылка на карточку.

#### 2.2. Скрейпер 2ГИС (`twogis_scraper.py`)
* **Инициализация**: Playwright с подпиской на сетевые запросы `page.on("response")`.
* **Перехват API**:
  * Открытие `2gis.ru` $\rightarrow$ ввод запроса.
  * Перехват запроса к `catalog.api.2gis.com/3.0/items` для захвата актуального API-ключа сессии и заголовков.
* **Пагинация через HTTPX**:
  * Отключение рендеринга страницы.
  * Прямые асинхронные HTTP-запросы к API пачками по 20–50 элементов с задержками 1.5–2 сек.
* **Маппинг данных**: нормализация полей 2ГИС к единой схеме `Organization` (вычленение сайтов, соцсетей из `contact_groups`, телефонов).

### Фаза 3. Модуль глубокого аудита сайтов (`site_auditor.py`)
Асинхронный воркер на базе `httpx.AsyncClient` и `selectolax.parser.HTMLParser` с пулом в 5–10 параллельных потоков и жестким таймаутом (5 сек на соединение, 5 сек на чтение).
* **Маршрутизация ссылок**:
  * Если сайт отсутствует $\rightarrow$ статус `NO_SITE`.
  * Если ссылка ведет на соцсеть (VK, Telegram, Taplink):
    * Проверка доступности ссылки.
    * При 404/ошибке $\rightarrow$ статус `BROKEN_SOCIAL_LINK`.
    * При успехе $\rightarrow$ статус `ONLY_SOCIAL`.
* **Проверка главного домена**:
  * **SSL/HTTPS**: попытка запроса по HTTPS, фиксация `ssl_error`.
  * **HTTP Status**: фиксация кодов 4xx/5xx или недоступности хоста.
  * **Адаптивность**: проверка наличия `<meta name="viewport">` в `<head>`.
  * **Аналитика**: поиск сигнатур `mc.yandex.ru/metrika`, `ym(`, `gtag(`, `google-analytics.com`.
  * **CMS / Движок**: сканирование DOM-маркеров (`tilda-records`, `wp-content`, `bitrix`, `wix.com`).
  * **Определение даты последнего обновления**:
    * Проверка HTTP-заголовка `Last-Modified`.
    * Проверка даты в `robots.txt` $\rightarrow$ `/sitemap.xml` (парсинг свежих узлов `<lastmod>`).
    * Поиск текста футера по регулярным выражениям: `©\s*(\d{4})` и `\d{4}\s*[-—]\s*(\d{4})`.
  * **Сбор скрытых контактов**:
    * Поиск ссылок по маскам: `/contacts`, `/kontakty`, `/about`, `/rekvizity`, `/politika`, `/privacy`.
    * Обход найденных 1–2 страниц с парсингом `mailto:`, ссылок `tel:`, мессенджеров (`wa.me`, `t.me`) и ИНН организации.

### Фаза 4. Движок формирования оффера (`pitch_maker.py`)
Модуль трансляции технических флагов в понятный для менеджера текст:
* Если `status == 'NO_SITE'`:
  > «Компания не имеет сайта. Трафик с карт и контекстной рекламы не конвертируется. Предложить базовый лендинг/квиз с конверсией в заявку.»
* Если `status == 'ONLY_SOCIAL'`:
  > «Вместо сайта используется соцсеть/Taplink. Теряется поисковый SEO-трафик, нет сквозной аналитики. Предложить разработку полноценного сайта.»
* Если сайт есть, компиляция по списку проблем:
  * Нарушение SSL $\rightarrow$ «Браузер помечает сайт как опасный (нет SSL)»
  * Нет мобильной версии $\rightarrow$ «Сайт не открывается корректно на смартфонах»
  * Нет Метрики $\rightarrow$ «Не установлена аналитика (не отслеживается окупаемость рекламы)»
  * Копирайт $< 2023$ $\rightarrow$ «Сайт визуально заброшен (контент не обновлялся с {YYYY} года)»

### Фаза 5. Бэкенд API, Отчёты и WebSocket (FastAPI)
* **Эндпоинты REST (для фронтенд-разработчика)**:
  * **Поиск и аудит**:
    * `POST /api/search/start` — прием `{ niche: str, city: str, source: "yandex" | "2gis" | "all", limit: int }`, создание кампании поиска, запуск фонового таска, возврат `campaign_id` и `task_id`.
    * `POST /api/search/stop` — принудительная остановка текущей задачи с гарантированным закрытием браузера.
    * `POST /api/captcha/resolved` — сигнал от фронтенда, что пользователь прошел капчу в окне.
  * **Лиды и текущая выдача**:
    * `GET /api/leads` — пагинация, фильтрация по `campaign_id`, нише, городу, статусам (`has_ssl`, `is_adaptive`, `status` и т.д.).
    * `GET /api/leads/{id}/pitch` — получение сформированного оффера и скрипта звонка для выбранного лида.
  * **Вкладка «Отчёты» (История поисков)**:
    * `GET /api/reports` — история всех запусков: дата и время (`created_at`), ниша, город, источник карт, запрошенный лимит, факт найдено (`found_count`), статус (`COMPLETED` | `IN_PROGRESS` | `STOPPED` | `FAILED`).
    * `GET /api/reports/{campaign_id}` — детальный отчет по конкретному поиску со списком всех собранных организаций и агрегированной статистикой (сколько без сайта, сколько без SSL, сколько без Метрики).
    * `DELETE /api/reports/{campaign_id}` — удаление отчета и связанных организаций.
  * **Экспорт**:
    * `GET /api/export/excel?campaign_id={id}` — выгрузка отформатированного файла `.xlsx` на базе `openpyxl` (цветовая подсветка колонок, автоширина, кликабельные телефоны и ссылки).
* **WebSocket протокол (`/ws/{campaign_id}`)**:
  * Стриминг событий в реальном времени:
    * `FOUND_COUNT`: `{ current: 18, limit: 50, percent: 36 }` — для полосы прогресса.
    * `AUDIT_STATUS`: `{ domain: "art-dent.ru", step: "CHECKING_SSL" }` — для радара активности.
    * `NEW_LEAD`: отправка готового объекта лида в момент завершения его аудита (для мгновенного появления строки в таблице).
    * `CAPTCHA_REQUIRED`: `{ service: "yandex", message: "Требуется пройти капчу" }` — сигнал фронтенду включить алерт.
    * `COMPLETED`: завершение работы со статистикой.
    * `ERROR`: текст ошибки.

## 2. Глубокий анализ: уязвимости, архитектурные и логические дыры

### 2.1. Критические дыры в базе данных и моделях
1. **Коллизия `external_id UNIQUE`**:
   * *Проблема*: И у Яндекса, и у 2ГИС идентификаторы могут быть числовыми строками (например, `123456789`). Ограничение `external_id UNIQUE` вызовет ошибку `IntegrityError` при совпадении ID из разных источников.
   * *Решение*: Составной уникальный индекс `UniqueConstraint('source', 'external_id', name='uq_source_external_id')`.
2. **Отсутствие контекста поиска (Сессии / Поисковые кампании)**:
   * *Проблема*: В таблице `organizations` нет связки с поисковым запросом, городом или датой запуска кампании. Через неделю в базе будет каша из сотен компаний из разных городов без возможности фильтрации «показать лиды по вчерашнему поиску стоматологий в Казани».
   * *Решение*: Ввести сущность `search_campaigns` (`id`, `query`, `city`, `source`, `total_found`, `created_at`) и связь M:N или FK `campaign_id` в организациях.
3. **Связь `organizations` $\leftrightarrow$ `audit_results`**:
   * *Проблема*: Если организация уже была спарсена ранее, но пользователь запустил повторный поиск или повторный аудит (сайт мог обновиться), текущая схема не определяет: перезаписывать аудит, создавать дубликат или хранить историю?
   * *Решение*: `org_id` сделать либо `UNIQUE` (1:1, с обновлением записи `UPSERT`), либо хранить историю с признаком `is_latest: bool`. Обязательно добавить `ondelete="CASCADE"`.
4. **Отсутствие нормализации контактов**:
   * *Проблема*: Карты отдают телефоны в форматах: `+7 (495) 000-00-00`, `8 800 100-00-00`, `+74950000000`. При поиске дублей или клике `tel:` возникнет хаос.
   * *Решение*: Нормализовать телефоны в формат E.164 (`+7XXXXXXXXXX`) при сохранении.

### 2.2. Дыры и уязвимости в скрейпинге (Яндекс.Карты и 2ГИС)
1. **Логическая ловушка «Ровно 50 новых организаций» (Infinite Loop)**:
   * *Проблема*: Если по запросу в данном районе найдено всего 12 организаций, скроллер будет бесконечно крутить страницу вниз, пытаясь набрать 50 штук. Процесс зависнет навсегда.
   * *Решение*: Детектор конца выдачи: если после 3-4 попыток скролла количество карточек не изменилось или появился блок «Больше ничего не найдено» / «Ничего не найдено», сбор останавливается автоматически.
2. **Виртуализация DOM в Яндекс.Картах (DOM Virtualization)**:
   * *Проблема*: В актуальной версии Яндекс.Карт контейнер списка использует виртуальный рендеринг: при скролле вниз элементы сверху физически удаляются из DOM. Если пытаться взять все карточки селектором `page.locator(...)` в конце скролла, будут доступны только последние 10-15 штук!
   * *Решение*: Непрерывный сбор данных на лету в `Set[external_id]` по мере скролла.
3. **Хрупкость CSS-селекторов Яндекса**:
   * *Проблема*: Классы вроде `.scroll__container`, `.search-snippet-view` часто рандомизируются или меняются каждые несколько месяцев.
   * *Решение*: Использовать устойчивые структурные селекторы (`div[data-id]`, селекторы по `role="list"`, `role="listitem"`, `aria-label`).
   * *Альтернатива Pro*: Яндекс.Карты подгружают данные через внутренний API (`/maps/api/search` или инициализируют `window.__INITIAL_STATE__`). Перехват сетевых ответов JSON снижает вероятность поломки селекторов на 90% и увеличивает скорость сбора в 5 раз.
4. **Скрытие телефонов и сайтов в сниппетах**:
   * *Проблема*: В общем списке на Яндекс.Картах сайт и телефон отображаются не всегда (часто телефон скрыт под кнопкой «Показать телефон» или виден только при клике на саму карточку в детальный вид). Сбор только с карточек списка даст потерю до 40% сайтов и телефонов.
   * *Решение*: Если в превью-карточке нет сайта/телефона, скрипт должен кликать на карточку организации для открытия детальной панели, либо парсить метаданные карточки из ответов карты.
5. **Блокировка Chromium профиля в Windows (`launch_persistent_context`)**:
   * *Проблема*: В Windows, если процесс Playwright аварийно завершился или запущен второй поиск, папка `./browser_profile` блокируется системным lock-файлом `SingletonLock`. Следующий запуск упадет с ошибкой `Target page, context or browser has been closed`.
   * *Решение*: Реализовать очистку zombie-процессов или использовать уникальные контексты с сохранением только cookies/storageState в JSON-файл (`storage_state.json`), а не всего бинарного профиля.

### 2.3. Дыры в аудите сайтов (`site_auditor.py`)
1. **Уязвимость SSL-проверки и падение на самоподписанных сертификатах**:
   * *Проблема*: Если у сайта просрочен или самоподписан SSL, вызов `httpx.get("https://...")` выбросит исключение `ssl.SSLCertVerificationError` или `httpx.ConnectError`. Если это исключение не перехватить специфично, аудит для сайта прервется со статусом ошибки соединения, хотя на самом деле это важный признак: сайт живой, но `has_ssl = False`!
   * *Решение*:
     1. Запрос по HTTPS с проверкой сертификата.
     2. Если `SSLError`: фиксируем `has_ssl = False`, повторяем запрос с `verify=False` для проверки содержимого сайта.
2. **Редиректы сайтов на соцсети (VK / Telegram / Taplink)**:
   * *Проблема*: В карточке указан домен `company.ru`, но при открытии он делает HTTP 301/302 на `vk.com/company` или `t.me/...`. В исходном плане такой сайт будет классифицирован как обычный сайт, а не `ONLY_SOCIAL`!
   * *Решение*: Проверять `response.history` и финальный URL (`response.url`). Если финальный домен относится к соцсетям — переводить в статус `ONLY_SOCIAL`.
3. **Ненадежность определения адаптивности через простой поиск `<meta name="viewport">`**:
   * *Проблема*: У многих старых сайтов прописано `<meta name="viewport" content="width=1200">` (что делает сайт неадаптивным на смартфонах!). Простой факт наличия тега даст ложноположительный результат.
   * *Решение*: Проверять содержимое `content`: обязательно наличие `width=device-width` или `initial-scale=1`.
4. **Ложные срабатывания Last-Modified и дат**:
   * *Проблема*: Заголовок `Last-Modified` у 85% сайтов генерируется Nginx/CDN на лету и равен текущему времени запроса. Sitemap может обновляться автоматически CMS-плагином ежедневно без изменения контента страниц.
   * *Решение*: Приоритет отдавать проверке копирайта в подвале:
     1. Парсинг `© 2012-2021` или `2018 ©`.
     2. Если копирайт выводится динамически через JS (`new Date().getFullYear()`), в HTML от `httpx` будет либо пусто, либо скрипт. Фиксировать fallback.
5. **Мусор при сборе Email и Телефонов**:
   * *Проблема*: Регулярка по сырому HTML соберет картинки (`bg@2x.png`), системные почты (`info@wix.com`, `support@tilda.cc`, `domain@example.com`, `webpack@...`) и телефоны веб-студий из подвалов («Создание сайтов: +7...»).
   * *Решение*:
     * Строгий черный список доменов email (`wix.com`, `tilda.ru`, `sentry.io`, `example.com`, `placeholder.com`, расширения `.png`, `.jpg`).
     * Парсинг в первую очередь ссылок `<a href="mailto:...">` и `<a href="tel:...">`.

### 2.4. Дыры в управлении задачами и WebSocket (FastAPI)
1. **Зомби-процессы при остановке задачи (`/api/search/stop`)**:
   * *Проблема*: При вызове `asyncio.create_task` и последующем `task.cancel()` Playwright в Windows часто оставляет запущенный дочерний процесс `chrome.exe`. Через 5-10 запусков память сервера переполнится процессами Chromium.
   * *Решение*: Менеджер фоновых задач (`TaskManager`), который при остановке явно вызывает `browser.close()` и `context.close()` в блоке `finally`.
2. **Обрыв WebSocket при перезагрузке страницы клиентом**:
   * *Проблема*: Если пользователь нажал F5 или закрыл вкладку, попытка бэкенда отправить лог в закрытый WebSocket выбросит `WebSocketDisconnect` и может прервать фоновую задачу сбора.
   * *Решение*: Безопасная отправка `broadcast` с перехватом ошибок отключения. Фоновая задача должна продолжать работу независимо от наличия активных слушателей WebSocket.
3. **Отсутствие валидации лимитов**:
   * *Проблема*: Если передать `limit: 5000`, Playwright будет работать часами и будет заблокирован антифрод-системами.
   * *Решение*: Ограничить `limit` значением от 10 до 200 (рекомендуемый дефолт 50).

### 2.5. Проблемы запуска и DX (Developer Experience) на Windows
1. **Проблема раздельного запуска Vite и FastAPI**:
   * *Проблема*: Скрипт `start.bat`, запускающий одновременно Uvicorn и Vite, часто блокирует консоль или требует два отдельных окна, что неудобно пользователю.
   * *Решение*:
     * *Режим разработки*: `start.bat`, запускающий бэкенд и фронтенд в двух параллельных окнах с цветными заголовками.
     * *Режим одного клика (Production/Local)*: Сборка фронтенда (`npm run build`) в папку `frontend/dist`, которую FastAPI раздает как статическую страницу (`StaticFiles`). Вся система запускается одним скриптом `python main.py` на порту 8000!

## 4. Обновленный пошаговый план реализации

### Этап 1: Доработка схемы БД и хранилища (SQLAlchemy Async + SQLite)
1. Создать модели:
   * `SearchCampaign`: история запусков (`id`, `query`, `city`, `source`, `target_limit`, `found_count`, `status`, `created_at`).
   * `Organization`: уникальность по `(source, external_id)`, нормализованные контакты, связь с кампанией.
   * `AuditResult`: флаги аудита, безопасные поля, `pitch_text`, `lead_score` (индекс горячести лида от 1 до 10 для менеджера).
2. Настроить автомиграции / инициализацию таблиц при старте.

### Этап 2: Скрейпер Яндекс.Карт с антифрод-защитой и стримингом
1. Настроить Playwright с stealth-параметрами (отключение webdriver флагов, реалистичные user-agent и viewport).
2. Реализовать непрерывный сбор данных из виртуализированного списка.
3. Добавить надежный детектор капчи (SmartCaptcha) с отправкой сигнала через WebSocket и паузой задачи до решения.
4. Добавить детектор конца выдачи (таймаут отсутствия новых карточек).
5. Извлечение полных данных: переход в карточку при отсутствии сайта/телефона в сниппете.

### Этап 3: Высокоскоростной скрейпер 2ГИС
1. Интеллектуальный сбор: получение первичного ключа API 2ГИС через Playwright/сетевой перехват.
2. Пагинация через асинхронный `httpx` с рандомизированными паузами (1.2–2.5 сек).
3. Нормализация данных под общий контракт `OrganizationCreate`.

### Этап 4: Модуль аудита сайтов (`SiteAuditor`)
1. Проверка URL: соцсети $\rightarrow$ `ONLY_SOCIAL` / `BROKEN_SOCIAL_LINK`.
2. Двухфазная проверка HTTPS (сначала строгая проверка SSL, при ошибке — повторный запрос без верификации для фиксации `has_ssl=False`, но сохранения анализа контента).
3. Парсинг HTML через `selectolax` (скорость в 10 раз выше `BeautifulSoup`):
   * `<meta name="viewport" content="...width=device-width...">` (настоящая адаптивность).
   * Поиск Метрики, Google Analytics, пикселей VK.
   * CMS-детекторы (Tilda, WordPress, Bitrix, Wix, InSales, Shopify).
   * Парсер года копирайта с защитой от фейковых дат.
   * Поиск контактов на страницах контактов (`/contacts`, `/about`).
   * Фильтрация мусорных email и нормализация телефонов.

### Этап 5: Движок офферов и Lead Score (`PitchMaker`)
1. Расчет `LeadScore` (0-100 баллов привлекательности лида для агентства):
   * Нет сайта: 100 баллов (продажа разработки лендинга под ключ).
   * Только соцсеть: 85 баллов (продажа сайта для конверсии трафика).
   * Нет SSL + нет мобильной версии: 75 баллов (критические проблемы, грозящие потерей клиентов).
   * Нет аналитики: 60 баллов (продажа настройки рекламы и Метрики).
   * Сайт заброшен (> 3 лет без обновления): 70 баллов (редизайн).
2. Генерация структурированного скрипта для менеджера:
   * «Боль клиента»
   * «Предложение решения»
   * «Первая фраза для звонка»

### Этап 6: FastAPI Backend, TaskManager и WebSocket
1. `TaskManager` для безопасного управления жизненным циклом фоновых задач (старт, пауза, остановка, очистка Chromium).
2. Потокобезопасный `ConnectionManager` для WebSocket со стримингом прогресса (`FOUND_COUNT`, `AUDIT_STATUS`, `NEW_LEAD`, `CAPTCHA_REQUIRED`).
3. Обработка капчи: эндпоинт `/api/captcha/resolved` для возобновления парсинга после ручного ввода.

### Этап 7: Модуль «Отчёты» (Reports), Экспорт в Excel и OpenAPI
1. Эндпоинты истории поисков (`GET /api/reports`, `GET /api/reports/{id}`, `DELETE /api/reports/{id}`).
2. Агрегированная статистика кампании (общее число найденных, с сайтами/без сайтов, процент с SSL, CMS и т.д.).
3. Экспорт в красивый Excel (`openpyxl`): цветовая заливка статусов (зеленый/желтый/красный), кликабельные ссылки на сайты и карточки карт, автоподбор ширины ячеек.
4. Детальное описание схем данных OpenAPI/Swagger (`/docs`) для удобной интеграции фронтенд-разработчиком.

### Этап 8: Скрипт запуска Backend и проверка зависимостей
1. Скрипт `run_backend.bat` / `run.py` для старта FastAPI-сервера с авто-проверкой наличия виртуального окружения и установленных браузеров Playwright.
2. CORS-конфигурация для беспрепятственного подключения фронтенда с любого локального порта (5173, 3000 и др.).
